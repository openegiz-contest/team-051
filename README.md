# ГОК «Степное»: сквозной баланс массы на OpenEgiz

Цифровой двойник вымышленного железорудного ГОК: экскаватор, два самосвала,
обогатительная фабрика, 3D-склад и пять вагонов. Решение для финансовых
контролеров, аудиторов и руководства: сопоставляет физические потоки и
учетные остатки, показывает неподтвержденную массу и сохраняет команды
сценария в журнале. Концепция команды — в [SUBMISSION.md](SUBMISSION.md).

Весь поток данных **синтетический**. LiDAR, GPS, ERP и весовые моделируются.
Конфигурационные данные OpenMines используются как открытый ориентир для
калибровки скорости и длительности рейсов; сверка, версия источника и
собственные допущения приведены в [SUBMISSION.md](SUBMISSION.md).
При запуске внешние датасеты не скачиваются; параметры заданы в исходниках.
Встроенный 3D-вид — изометрическая low-poly диорама Three.js с мягкими тенями,
составными моделями техники, плавным движением и независимой учетной сеткой склада.

## Запуск с нуля: буквальные команды для сборщика

Целевая среда сборщика — **Ubuntu 24.04 LTS (24.04.5 по ТЗ)**.
Также поддерживаются Linux amd64/arm64 либо Ubuntu в WSL2; нужен Docker Engine/Desktop с доступным
демоном, Docker Compose **2.24.4+**, минимум 6 ГБ памяти Docker, Git, Bash, curl,
make. Для первой сборки необходим интернет (образы Docker, PyPI и исходники
штатного extended API платформы). Windows: Docker Desktop с WSL integration;
команды ниже выполняются **в Ubuntu**, не в PowerShell. Подготовка WSL —
[OPENEGIZ.ru.md](OPENEGIZ.ru.md).

На чистой Ubuntu сначала установить утилиты, в том числе **пакет `make`**.
Эти команды выполняются до первого `make up`:

```bash
sudo apt-get update
sudo apt-get install -y git make curl ca-certificates python3
make --version
python3 --version
```

Docker устанавливается отдельно: на чистом Linux использовать
[официальную инструкцию для Ubuntu](https://docs.docker.com/engine/install/ubuntu/)
с пакетами Docker Engine, Buildx и Compose plugin; в WSL — интеграцию
Docker Desktop из инструкции выше. Перед запуском проверить, что текущему
пользователю доступен работающий демон и установлен Compose 2.24.4+:

```bash
docker version
docker compose version
```

Из чистого каталога, с настроенным доступом GitHub к репозиторию команды:

```bash
git clone https://github.com/openegiz-contest/team-051.git
cd team-051
make up
make team-smoke
```

Если репозиторий уже предоставлен сборщику, перейти в его корень и выполнить
последние две команды. `make example-mine` не требуется.

`make up` генерирует пароли в `deploy/compose/.env`, собирает сервис команды,
запускает OpenEgiz, создает 18 двойников с иерархией и автоматически подключает
три дашборда. Начальные остатки — 3000 т концентрата; телеметрия идет сразу.
Моделирование ускорено в 30 раз: один реальный тик в секунду равен 30 с модели.
Первые разгрузки руды появляются примерно через 20 секунд после старта сервиса,
первая отправка пяти вагонов — примерно через 210 секунд. Графики InfluxDB
отстают от состояния модели на период сброса Telegraf, обычно около 10 секунд.

Дождаться успешного завершения обеих команд. `make team-smoke` проверяет
двойники, Grafana, производственный цикл, команды `0 → 1 → -1 → 0`, изменение
состояния Ditto и запись аномалии в InfluxDB. В конце сценарий выключен.
Ошибки приводят к ненулевому коду выхода; ручной импорт JSON не нужен.

Буквальный эквивалент запуска без make (из корня):

```bash
bash scripts/compose-env.sh
bash scripts/compose-preflight.sh
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml up -d --build --wait --wait-timeout 900
bash scripts/compose-wait-ready.sh
bash scripts/compose-urls.sh
bash scripts/team-smoke.sh
```

Сервис команды зависит от успешного завершения `init` и `stepnoe-setup`;
`stand` становится healthy только после запуска Grafana и модели.

## Что открыть

Открыть [Grafana](http://localhost:3000), войти как `admin` с паролем,
напечатанным `make up`. Пароль **не** `admin`. При необходимости посмотреть
только его:

```bash
sed -n 's/^GRAFANA_ADMIN_PASSWORD=//p' deploy/compose/.env
```

После входа доступны:

| Адрес | Содержимое |
|---|---|
| [Executive Overview & 3D Mine View](http://localhost:3000/d/stepnoe-overview) | 3D-склад, фабрика, самосвалы, остатки и физические потоки |
| [Mass Balance & Anti-Fraud Audit](http://localhost:3000/d/stepnoe-audit) | Балансы массы/Fe, учет против 3D-скана, статус и переключатель |
| [Logistics & Geofencing](http://localhost:3000/d/stepnoe-logistics) | Координатная карта, следы техники, коридоры ±150 м, загрузка вагонов |
| [Полный интерфейс стенда](http://localhost:3000/stepnoe/) | Все три представления и журнал команд на одной странице |

В Grafana: **Dashboards → Stepnoe**. Иерархия двойников — в приложении
**OpenEgiz → Twins**, корень `org.stepnoe:Stepnoe`. Для платформы 1.0.4
иерархию задает строковый атрибут `_parents`; также записывается `parents[]`.
3D-вид и карта читают двойники из API Ditto; графики Grafana — из InfluxDB.
Состояние модели напрямую в визуализацию не передается (правила, п. 6.2).
Все браузерные запросы идут через один адрес стенда; менять порты в JSON
или устанавливать плагины вручную не требуется. Если изменен `GRAFANA_PORT`
в `.env`, использовать соответствующий порт в браузере.

## What-if: Simulate Paper Fraud

На дашборде аудита выбрать **Приписка в отчете (+300 т)** или
**Сокрытие остатка (−300 т)** и включить **Simulate Paper Fraud**. Направление
можно менять и при включенном сценарии. Команда публикуется в
`telemetry/stockpile/inject_fraud`; модель оставляет физические датчики
неизменными и меняет только учетный остаток на **±300 т**. Оба направления
дают красный статус `CRITICAL ANOMALY: Mass Balance Mismatch` и расхождение
графиков. Выключить переключатель
или нажать «Сбросить сценарий»: статус возвращается к `BALANCE OK`, журнал
сохраняется. Кнопка дожидается подтверждения нового состояния.

Точные команды MQTT, не требующие MQTT-клиента на машине сборщика:

```bash
# ON
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T mosquitto mosquitto_pub -h localhost -t telemetry/stockpile/inject_fraud -m 1 -q 1 -r
# Сокрытие остатка
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T mosquitto mosquitto_pub -h localhost -t telemetry/stockpile/inject_fraud -m -1 -q 1 -r
# OFF / RESET
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T mosquitto mosquitto_pub -h localhost -t telemetry/stockpile/inject_fraud -m 0 -q 1 -r
```

Команды: `1` — приписка, `-1` — сокрытие, `0` — сброс. Повтор команды
не накапливает расхождение. HTTP API принимает те же числа в `{"value":-1}`,
`{"value":0}`, `{"value":1}` через прежний CORS POST `/stepnoe/api/fraud`.
Retained-команда и SQLite сохраняют сценарий при перезапуске. Сброс передается
как retained `0`. 300 т равны 10% **начального** склада, процент от текущего
остатка вычисляется динамически, поэтому не зашит как 10.4%.

Для режима строго ±10% от текущей массы добавить строку `FRAUD_MODE=percent`
в `deploy/compose/.env` и повторить `make up`. По умолчанию `FRAUD_MODE=fixed`.
Аналогично `SIM_SPEEDUP=30` задает ускорение времени.

Режим `FRAUD_MODE=drift` накапливает подписанное расхождение со скоростью
`FRAUD_DRIFT_RATE_TPH=5` т за виртуальный час. Управление остается прежним:
`1` — накопительная приписка, `-1` — накопительное сокрытие, `0` — сброс
накопления. Повтор команды не сбрасывает накопленное значение; смена знака
сохраняет его модуль. Тревога возникает при `|residual| > 1 т`, поэтому
небольшой drift сначала остается ниже порога. Состояние и накопление
сохраняются в SQLite вместе с моделью.

Обслуживание доступно для `Processing_Plant`, `Truck_01`, `Truck_02`:

```bash
# Остановить фабрику; для возобновления отправить -m 0 в тот же топик.
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T mosquitto mosquitto_pub -h localhost -t telemetry/control/maintenance/Processing_Plant -m 1 -q 1 -r
# Остановить самосвал, сохранив текущий груз, координаты и этап рейса.
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T mosquitto mosquitto_pub -h localhost -t telemetry/control/maintenance/Truck_01 -m 1 -q 1 -r
```

HTTP-эквивалент — POST `/stepnoe/api/maintenance` с JSON
`{"thing":"Processing_Plant","value":1}`; `value:0` возобновляет работу.
Ответ 202 подтверждает прием MQTT-команды; GET `/stepnoe/api/maintenance`
возвращает подтвержденные состояния объектов из Ditto и отдельный журнал
обслуживания. Существующий `/stepnoe/api/audit` остается журналом фрода.
Retained-команды обслуживания сохраняются в брокере: после демонстрации
нужно явно отправить `0` для каждого остановленного объекта.

При обслуживании фабрики руда от самосвалов накапливается в `buffer`,
переработка и прирост концентрата/хвостов останавливаются. `raw_inflow`
по прежнему контракту остается накопленным счетчиком сухих тонн;
новое поле `raw_inflow_rate` измеряется в т/ч и при остановке равно **0**.
Самосвал передает статус `MAINTENANCE` и скорость 0; после возобновления
продолжает прерванный этап. Остальная техника и ЖД работают независимо.

## Каскадные сценарии: запуск и отмена

Открыть «Анти-фрод и аудит» → **«Причина → последствия → решение»**.
«Запуск» и «Сброс» ждут подтверждения Ditto; HTTP 202 означает только прием
команды. Панель работает на автономном сайте и внутри Grafana.

| Сценарий | Запуск и последствия | Отмена |
|---|---|---|
| Фабрика / ERP (`plant_erp`) | Переработка 0 т/ч, ERP начисляет 400.8 т сухого концентрата/ч. Буфер достигает 100%, самосвалы стоят с оставшимся грузом, очередь из двух машин переводит экскаватор в `IDLE`. Аудит: `ERP_DURING_DOWNTIME`, красный `CRITICAL ANOMALY: Mass Balance Mismatch`. | «Сброс» возобновляет фабрику и обнуляет только сценарную ERP-поправку. Запасы и журнал сохраняются; очередь освобождается при переработке. |
| Смещение весового канала (`sensor_bias`) | Показания весов завышены на 2%; масса, потоки и LiDAR неизменны. Аудит: `SENSOR_MISMATCH`, рекомендация «Проверить измерительный канал». | «Сброс» возвращает калибровку; после свежих согласованных измерений тревога снимается. |

POST `/stepnoe/api/scenarios`: `{"scenario":"plant_erp","value":1}` либо
`{"scenario":"sensor_bias","value":1}`; `value:0` отменяет выбранный сценарий.
GET возвращает состояния и журнал. MQTT-топики:
`telemetry/control/scenario/plant_erp` и `telemetry/control/scenario/sensor_bias`,
payload `0|1`, retained, QoS 1. Повтор команды не сбрасывает накопление.
Журнал сценариев хранится отдельно; контракт `/api/audit` сохранен.
Ручной maintenance и сценарная остановка независимы: сброс сценария не
отменяет вручную установленное обслуживание.

### Дождь и устаревшая влажность

В панели сценариев нажать «Запуск» в карточке дождя. `rain` меняет фактическую
влажность с 3% на 7%, сохраняя сухую массу и Fe. ERP продолжает применять
коэффициент 1.03. Для 3000 т сухой массы: `wet=3210 т`,
`ERP=3210/1.03=3116.5049 т`, ошибка +116.5 т. Рекомендация:
**«Требуется пересчет влажности / ошибка ERP»**, причина `MOISTURE_ERP_MISMATCH`.
«Сброс» возвращает базовую влажность; дождаться свежего показания весов.
Управление: POST `/stepnoe/api/scenarios` с `{"scenario":"rain","value":1|0}`
или MQTT `telemetry/control/scenario/rain`, payload `1|0`, retained QoS 1.
Сброс моделирует мгновенное высыхание; испарение и движение воды не считаются.

Приборные двойники: `Weighbridge_01` (фабрика), `LiDAR_01` и
`Moisture_Sensor_01` (склад), `ERP_Register` (фабрика). Каждый имеет статус,
калибровку, задержку и метку времени. Весы публикуют влажное показание;
аудит приводит его к сухому через влажность на том же времени. ERP хранит
свою зарегистрированную влажность отдельно. Прежние поля телеметрии сохранены.
Подписка источника Ditto `telemetry/+` переведена на QoS 1; повторы возможны,
состояния идемпотентны, а применение подтверждается через Ditto и InfluxDB.

## Физическая модель и ограничения

Все прежние поля массы и баланс Fe приведены к сухому веществу.
В базовом сценарии влажность фиксирована на **3.0% по сухой основе**,
как `moisture_pct=3.0` в модели и `MOISTURE_PCT=3` в конфигурации
(отношение воды к сухому веществу):
`wet_stock = dry_stock × (1 + moisture_pct / 100)` и
`dry_stock = wet_stock / (1 + moisture_pct / 100)`.
Поэтому начальные 3000 т сухого запаса соответствуют 3090 т влажного.
Оба остатка передаются отдельно; `moisture` передается складом и фабрикой.
2.7 т/м³ — принятая **эффективная насыпная плотность сухого вещества**;
`wet_density = 2.7 × (1 + moisture_pct / 100)` учитывает воду при том же
геометрическом объеме. Геометрия синтетического
скана — эллиптический конус с полуосями 25 и 15 м:
`V = π × 25 × 15 × h / 3`, `M = ρ × V`. Визуализация показывает эту геометрию;
реальные облака точек не обрабатываются. Поворот сцены — перетаскиванием,
масштаб — колесом, выбор объекта — кликом.

`team/sensors.py` отделен от физики: `reconcile()` принимает только пакеты
измерений и учетный регистр, без доступа к модели и истинной массе.
Накопительные весы интегрируют импульсы физических перемещений продукта,
задерживают их на 5 с модели и добавляют погрешность ±0.06 т (σ=0.02 т).
LiDAR интегрирует растровые отсчеты поверхности конуса; калибровка единичного
конуса устраняет ошибку дискретизации. Скан раз в 10 с поступает с задержкой
10 с. Общая гауссова ошибка имеет σ=0.5% / 3; три головки добавляют собственные
ошибки σ=0.5% / 6 к своим секторам. Отсчеты ограничены ±0.5% перед интеграцией.
Это синтетическая съемка поверхности, а не обработка реальных облаков точек.

`ground_truth_mass` и прежний `physical_stock` — эталон симуляции;
`weight_scale_reading` / `measured_stock` — показания весового канала;
`lidar_volume_reading` / `scan_volume` — задержанный объем;
`lidar_dry_stock` — сухой массовый эквивалент скана. Метки `scale_timestamp`
и `lidar_timestamp` заданы в виртуальных секундах от старта модели.
ERP — отдельный регистр выпуска и погрузки, а не копия истинной массы.
Для сверки он приводится к времени соответствующего измерения.

При складе 3000 т шум LiDAR может означать ±15 т. Из расхождения скана и ERP
сначала вычитается калиброванный допуск; для весов вычитается 0.06 т.
Тревога возникает, когда модуль **остатка после допуска >1 т**.
Внутренние остатки сохранения массы/Fe не включаются в это решение.
Весы и LiDAR сравниваются с поправкой на разные timestamps;
расхождение каналов классифицируется отдельно от ошибки учета.

`SENSOR_FALSE_ALARM_PROBABILITY=0.000001` задает вероятность редкого
совпадения ошибок обоих каналов на скан (0.0001%). Такой выброс добавляет
по 3 т к показаниям, не меняя физику, и может вызвать ложную тревогу.
Это заданная вероятность синтетического сбоя, а не измеренная точность
реального прибора. Генераторы, задержанные пакеты и история ERP сохраняются;
чтение API не меняет измерения. Утрата меньше погрешности LiDAR может быть
неразличима до независимого подтверждения весами.

По умолчанию склад ограничен 6000 т сухого вещества, буфер — 360 т,
допустимая очередь — одна машина. При очереди больше лимита экскаватор
переходит в `IDLE`. Заполненный склад останавливает переработку фабрики.
Бункер принимает груз только в свободное место; остаток остается в кузове.
Масса не отбрасывается. Настройки: `MAX_STOCK_CAPACITY`,
`MAX_BUFFER_CAPACITY`, `MAX_TRUCK_QUEUE`. При чтении старого checkpoint без
лимитов емкость расширяется до уже сохраненного запаса, если он больше
стандартного. Тонны не удаляются. Последующее превышение лимита блокируется;
явная конфигурация меньше сохраненного запаса отклоняется с ошибкой.

В Ditto сохранены прежние 14 объектов и иерархия `_parents` / `parents`;
добавлены четыре прибора и связи `feeds_to`,
`measured_by`, `audit_inputs`, типизированные `feature_contracts` с единицами
сухой/влажной массы и временем датчиков. На графике видны LiDAR и ERP;
«Эталон симуляции» включается отдельно для отладки и не используется аудитом.
Аналогичный эталон Grafana скрыт по умолчанию; показать его можно через легенду.

3D использует OrthographicCamera, Ambient/Directional/PointLight и мягкие
PCF-тени. HTML-лейблы следуют за моделями; Raycaster показывает скорость,
груз и состояние. Позиции и повороты сглаживаются между снимками Ditto,
вращение колес связано с пройденным расстоянием, стрела экскаватора и
конвейер работают при соответствующем состоянии процесса. При потере
свежих данных рабочие анимации останавливаются. Красная полупрозрачная
сетка показывает объем учетного остатка, физическая геометрия остается
неизменной при переключении фрода. Оба конуса используют общий масштаб;
отношение их геометрических объемов равно отношению масс.

Объекты собраны программно из геометрии Three.js без GLB. Размеры и взаимное
расположение предприятий на диораме схематические. Карта самосвалов —
двухполосная замкнутая схема: верхняя полоса с рудой к фабрике, правая дуга
разгрузки, нижняя полоса возврата и левая дуга погрузки с карманом ожидания.
Прогресс следует GPS, состоянию, загрузке и числу рейсов из Ditto; при наличии
поля `elapsed` оно уточняет фазу. Между снимками маркеры проходят по петле,
не срезая через середину. ЖД-карта использует географическую проекцию.
Фабрика увеличена в 1.6 раза. Перед ее приемным бункером устроена проездная
разгрузочная площадка с колосниковой решеткой. Середина разворотной петли —
фиксированная точка `unloading`: самосвал останавливается, поднимает кузов
и затем выходит на обратную полосу. Даже если HTTP-опрос пропустил короткое
состояние разгрузки, показанный рейс выдерживает остановку у приемника.
Склад расположен в ангаре с металлическими фермами, оболочкой прозрачностью
0.32 и тремя направленными LiDAR-головками. Конвейер выходит из внешнего
патрубка фабрики, проходит через открытые верхние торцевые пролеты ангара
над штабелем и спускается в ЖД-бункер над центральным вагоном.
Конус склада строится по `LiDAR_01.volume` (`lidar_volume_reading` в аудите).
Постоянный `MAX_CAPACITY=6000` задает шкалу 0–6000 т: размер растет и после
3000 т, без нормировки на текущую массу. Возраст скана и погрешность ±%
показаны под сценой. При превышении диапазона старым checkpoint конус
ограничен границей шкалы с явной отметкой, численные показания не обрезаются.
Учетная сетка может выходить за границу склада до 112% шкалы; превышение
диапазона не меняет данные аудита. Истинный эталон скрыт под «Отладочный режим».
Рядом расположен погрузочный узел: локомотив и пять вагонов закреплены
в диораме, без анимации движения. Фактическое движение вагонов по 65-км
маршруту показано на GPS-карте. Экскаватор использует целевые позиции и
кватернионы с коэффициентом сглаживания 0.04 при 60 FPS; самосвалы двигаются
по замкнутой кривой, описанной ниже. Панель виртуального времени
закреплена справа вверху и показывает время из Ditto, включая Grafana.
Delta time для 3D берется из `THREE.Clock`. Самосвалы следуют единой замкнутой
`CatmullRomCurve3`: телеметрия меняет только целевой прогресс, а текущий
непрерывно растет с ограничением скорости и ускорения, включая переход 1 → 0.
Координаты и направление вычисляются по самой кривой, без срезания углов
пространственным lerp. Небольшие колебания GPS не возвращают самосвал назад.
При скрытии вкладки или переключении режима циклы 3D и 2D останавливаются.
При возврате прогресс, позиция, ориентация и скорость синхронизируются с
актуальной телеметрией без воспроизведения пропущенных кругов; первый новый
снимок дополнительно устраняет возможное отставание фонового HTTP-опроса.
Delta time ограничен 0.1 с. Обход фабрики вынесен на запад и в переднюю
свободную зону; габарит самосвала проверяется по всей петле. Асфальт имеет
повторяющуюся CanvasTexture с желтым центральным пунктиром и светлыми
краевыми линиями; UV и повторение согласованы с длиной дороги.
Съезд проложен вдоль северной и восточной стенок карьера; под ним вырезан рельеф той же
высоты. Полотно поднято на 0.15 м и использует polygonOffset. Конвейер выходит
через внешний узел разгрузки, обходя стену, крышу и восточный силос фабрики.

На `/stepnoe/` доступны вкладки «Обзор рудника», «Логистика и техника» и
«Анти-фрод и аудит». Они меняют секции и URL без перезагрузки; работают
«Назад» и «Вперед», сохраняются состояние сцены и управление фродом.
При прямом открытии `?view=mine|map|audit` шапка и вкладки всегда видны,
в том числе после F5; параметр `view` определяет активную вкладку.
Только внутри iframe Grafana шапка и переключатель скрыты — используется
компактный встроенный вид. Подсказки метрик открываются вниз, поверх панелей.
Three.js 0.180.0 и OrbitControls поставляются локально в `team/web/vendor/`
с MIT-лицензией. Для 3D нужен WebGL 2. Inter подключен через Google Fonts,
при отсутствии интернета используется системный шрифт. Дополнительная
сборка JavaScript не требуется.

Самосвалы: 90 т, четыре ковша по 22.5 т, погрузка 120 с, рейс 360 с,
разгрузка 40 с, возврат 360 с, скорость в телеметрии 30 км/ч. Порядок времени
и скорости сверен с открытой конфигурацией
[OpenMines](https://github.com/370025263/openmines/blob/acd77e23de2c3b743485ec87cabdbbf7779ceb3e/openmines/src/conf/north_pit_mine.json);
это сверка параметров, а не статистическая подгонка по полевым рейсам.
Фабрика: до 600 т **сухой сырой руды/ч**, Fe входа 43–45%,
извлечение железа 83.5%, Fe концентрата 55%. Выход концентрата рассчитывается
как `feed × grade × recovery / 0.55`, хвосты — как разность масс; железо
хвостов учитывается отдельно. Вагоны по 70 т, загрузка 200 т/ч, ЖД-коридор
65 км при 40 км/ч. Точки на карте условные, объект вымышленный.

За 30 суток полной непрерывной загрузки предел переработки равен
`600 × 24 × 30 = 432 000 т` сухого сырья. При Fe входа 44% расчетный выпуск
концентрата — `432 000 × 0.44 × 0.835 / 0.55 = 288 576 т` сухого вещества.
Это верхний расчетный режим; простои и недостаток сырья снижают выпуск.
Пример накопленного учетного разрыва 300 000 т в концепции получен как
`2500 т/месяц × 12 × 10 лет`, примерно 0.866% номинального месячного
выпуска концентрата. Этот аналитический пример отличается от исполняемого
`drift` по умолчанию: 5 т/ч дают 3600 т за расчетный месяц в 720 ч.
Десятилетний прогон с результатом 300 000 т не заявляется.

Проверяются уравнения сохранения физической модели и учетный остаток.
Здесь `physical_stock` — внутренний физический запас текущей реализации,
а шумная оценка LiDAR передается отдельно как `lidar_dry_stock`.
Эти диагностические уравнения не участвуют в решении `reconcile()` и
не выдаются за сверку реальных датчиков:

```text
Фабрика: feed − concentrate − tails = 0
Склад:   opening_stock + concentrate − rail_loaded − physical_stock = 0
ГОК:     opening_stock + mined − tails − shipped
         − (physical_stock + raw_buffer + truck_payload + wagons_on_site) = 0
Железо:  opening_Fe + mined_Fe − tails_Fe − shipped_Fe − inventory_Fe = 0
Учет:    opening_stock + concentrate − rail_loaded − book_stock = 0
```

Граница отгрузки — ЖД-весовая при отправлении полностью загруженных пяти
вагонов. Вагон в пути уже включен в `shipped`, поэтому второй раз в запасах
не учитывается. Порог аномалии — абсолютный остаток более 1 т. При потере
MQTT виртуальное время останавливается; после восстановления публикуются
полные состояния. Доставка MQTT QoS 1 подтверждает прием брокером;
сквозное применение в Ditto/InfluxDB проверяется отдельным smoke-тестом.

Карта строится локально без интернет-тайлов. Геозона вычисляется по расстоянию
до сегмента; штатные маршруты остаются внутри коридора. Отдельного сценария
съезда с маршрута сейчас нет. Следы карты хранятся в браузере, история
датчиков — в InfluxDB, команды и состояние — в Docker-томе `stepnoe-data`.
Текстовая панель Grafana разрешает локальный iframe; страницы требуют сессии
Grafana, а `/stepnoe/api/` доступен напрямую без ее авторизации и поддерживает
CORS (`Access-Control-Allow-Origin: *`, методы GET/POST/OPTIONS). Как и исходная платформа, стенд рассчитан на локальную среду
(MQTT без аутентификации). Полноценная интеграция ERP/IoT не реализована.

## Проверки и эксплуатация

```bash
make team-test                  # модель, датчики, блокировки, сценарии и API
node --test team/tests/web_api.test.cjs  # API, сценарии, геометрия и навигация (Node 18+)
make team-smoke                 # реальный сквозной тест, нужен запущенный стек
make smoke                      # штатный smoke-тест OpenEgiz
make ps
make logs S=stepnoe
make down                       # остановить, сохранив все данные
make up                         # продолжить с сохраненными остатками
```

`make team-test` требует Python 3.10+ на хосте; `team-smoke` выполняется внутри
контейнера и не требует Python на хосте. Для повторной генерации статических
моделей и дашбордов: `python3 team/generate_assets.py`.

`make clean` **удаляет все данные платформы, журнал, состояние и пароли**.
Использовать только для намеренного запуска с чистого состояния.

После обновления кода переключателя выполнить в том checkout, из которого
запущен стенд:

```bash
make up
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T stand nginx -t
docker compose -f deploy/compose/docker-compose.yml -f deploy/compose/stepnoe.yml exec -T stand nginx -s reload
```

`make up` пересобирает сервис с обновленным JS; reload применяет измененный
bind-mounted конфиг Nginx. Интерфейс и панели используют единый абсолютный
путь `/stepnoe/api/fraud`, который проксируется в `stepnoe:8085/api/fraud`
без подзапроса авторизации к Grafana. HTTP-сервер Stepnoe слушает внутренний
порт 8085; он не публикуется отдельно на хосте. Публичный порт extended API
платформы также имеет номер 8085, но относится к другому контейнеру.
Backend отвечает на OPTIONS статусом 204 и разрешает заголовки
`Content-Type, X-Grafana-Org-Id`. JavaScript задает `mode: 'cors'` и
`credentials: 'same-origin'`. Ошибки прокси отображаются сообщением;
HTML не разбирается как JSON.
